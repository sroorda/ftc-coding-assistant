# Three-Track Team Program

FTC software succeeds when beginners can reason about code, student leads can
coordinate safe changes, and mentors know how to help without becoming the team’s
programmers. These tracks use the same exercises but have different responsibilities.

## Choose a starting point

| Track | Start here | Finish when |
|---|---|---|
| A — Students | [Student learning path](tracks/students.md) | you can change, test, and explain the virtual intake project |
| B — Team Leads | [Team lead workshops](tracks/team-leads.md) | your team can move a small change through branch, review, and merge-ready status |
| C — Mentors | [Mentor playbook](tracks/mentors.md) | you can coach with graduated help and audit AI-assisted work |

Track A is sequential. Tracks B and C run alongside it and use student exercises as
practice material. They should not add process overhead to the first two student
sessions.

## Coordinated schedule

| Student session | Track A | Track B lead responsibility | Track C mentor focus |
|---|---|---|---|
| 1 | first program | observe setup friction; do not introduce branching yet | establish prediction and explanation norms |
| 2 | variables and math | model a small, readable commit | calibrate the help ladder |
| 3 | decisions and deadbands | workshop 1: branches and commits | coach debugging without supplying the fix |
| 4 | loops and autonomous | workshop 2: evidence-based review | separate syntax help from logic help |
| 5 | methods, classes, tests | workshop 3: project boundaries | use tests as feedback, not answer keys |
| 6 | virtual intake | workshop 4: architecture decision | assess understanding and assistant use |

## Shared definition of done

For training work, “done” means all five statements are true:

1. The author can explain every changed line.
2. The change is tied to a stated requirement.
3. The relevant lesson command runs and its result was read.
4. Normal, boundary, and failure behavior were considered where applicable.
5. A reviewer can distinguish student work from AI suggestions and knows how each
   accepted suggestion was verified.

## Handoffs between roles

- A student asks for a review only after making a prediction and running the work.
- A lead asks questions first, then records blocking findings separately from optional ideas.
- A mentor intervenes when safety, privacy, or learning boundaries are crossed—not
  merely because a solution is taking time.
- The student owns the final explanation. A lead or mentor may not explain on the
  student's behalf during the readiness check.

## Team health check

At the end of the sequence, choose one small, non-hardware change and walk it through
the complete system: student implementation, lead review, student revision, mentor
learning audit, and a final demonstration. If one person must take over to finish,
that step identifies the next training need.
